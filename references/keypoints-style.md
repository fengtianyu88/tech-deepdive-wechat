# 要点式技术拆解 · 写作规范

> 本文件是 skill 自带副本，供写作阶段直接加载。它与工作区根目录的《要点式技术拆解-写作规范.md》内容一致。
> 适用：中文技术写作。场景：技术原理讲解、方法对比、论文拆解、产品机制说明。

---

## 0. 一句话定义

把一篇技术说明拆成**四层骨架**：**分层标题 → 编号步骤 → 术语释义条目 → 收口句**。每一层只承担一件事，读者扫一眼就知道这一节在讲什么、有几条、谁先谁后。

**最容易理解错的地方**：以为要点式就是“多用项目符号”。不是。真正决定观感的是条目内部的 **名词—释义式对应（term–definition gloss）**，也就是“加粗名词 + 冒号 + 一句话机制 + 括号补注”这个格式。只加项目符号、内容仍是长句，味道完全出不来。

---

## 1. 四层骨架

| 层 | 承担什么关系 | 长什么样 |
|---|---|---|
| ① 章节标记 | 导航 | 一句直白短标题，说清这节讲什么 |
| ② 编号步骤 | 先后关系 | `1.` `2.` 编号，每步一句 |
| ③ 释义条目 | 并列关系 | 项目符号 + **加粗名词** + 冒号 + 一句话机制（括号补注） |
| ④ 收口句 | 从机制跳到结论 | “关键在于，……”或“也就是说，……” |

### ① 章节标记

- 标题必须**直白**，一句话说清这一节讲什么，读者看标题就能预判内容
- 长度控制在一行内，不超过 12 字
- **禁止**设问式、比喻式、悬念式标题
- emoji 前缀是**可配置项，默认关闭**；开启时用 `💡` `🔬` 等代替“一、二、三”做分节标记

| | 写法 |
|---|---|
| ✓ 正例 | `一、自反馈强化学习是什么` / `三、1017 涨分涨在哪了` / `四、奖励从人挪到了模型自己` |
| ✗ 反例 | `一、核心机制：从"试错"到"反思"`（比喻 + 冒号，绕了一层） |
| ✗ 反例 | `三、痕迹留在哪`、`四、监督信号一直在往里挪`（设问式 / 比喻式） |

### ② 编号步骤

只用于**有明确先后关系**的流程。并列关系不要用编号，用条目。

```
1. **{步骤名}**：{这一步做什么}。
2. **{步骤名}**：{这一步做什么}。
```

- 每步一句话，最多两行，不要在一序号下再挂子条目
- 步骤名也加粗，后接冒号
- 步骤数控制在 2–4 步；超过 4 步说明流程该分节了

### ③ 释义条目（本写作体的核心层）

```
- **{中文名词}（{英文名或缩写}）**：{一句话讲机制}（{括号里补一句解释或限定}）。{可选：一个具体数字或结果}。
```

- **名词先中文，英文名或缩写放括号里**。第一次出现给全称，之后可只用缩写
- 冒号后面**只能是一句话**，只讲“它怎么做”，不讲背景、不讲动机、不讲价值
- 括号补注负责拆掉读者最容易卡住的那个点，一句话，不超过 20 字
- 具体数字放条目末尾，**一条最多一个**，且必须能对上表或来源
- **绝对不展开成段**。单条控制在 150 字以内，超了要么拆成两条，要么把细节挪到正文散文里

| ✗ 常见写法（AI 默认产物） | ✓ 要点式写法 |
|---|---|
| GRPO 与自反馈的结合是一种将反馈-改进循环嵌入 GRPO 训练框架的方法，它通过设计专门的奖励函数来引导模型产出真正能提升答案质量的反馈，而不是空洞的重复。 | **GRPO 与自反馈的结合（iGRPO）**：先用优化时同一个标量奖励，从一组自采草稿里挑出最好的那份，再把它接回原问题后面做精修更新（不引入新的奖励模型）。AIME24 拿下 85.62%。 |

反例的问题：名词、机制、限定条件混在一句里，读者读第二遍才知道主语是谁。

### ④ 收口句

- 每节末尾**有且只有一句**
- 固定以“**关键在于，**”或“**也就是说，**”开头
- 作用是**从机制跳到结论**，不是复述上文、不是总结套话

| | 写法 |
|---|---|
| ✓ 正例 | 关键在于，它改变的不是某个单点能力，而是模型变强的路径。 |
| ✗ 反例 | 综上所述，自反馈强化学习代表了当前大模型训练的重要方向。（套话，零信息量） |
| ✗ 反例 | 以上就是本节的全部内容。（元叙述，读者不需要） |

## 2. 句式与标点约束

**允许**：中文标点用逗号切节奏；冒号用在条目名之后（本写作体核心格式，例外放行）；直接下判断（“我觉得”“可这只是我的推断”）。

**禁止**：

- 感叹号、破折号堆叠
- 起承转合套话：首先、其次、最后、综上所述、值得注意的是、总而言之
- 商业黑话：赋能、抓手、闭环、颗粒度、心智、势能、生态位
- 高频踩雷词：本质上、毫无疑问、众所周知、说白了、意味着什么
- 作者对文章本身的旁白：本文将从三个方面展开、接下来我们看（**AI 味最重的一类**）

**引号**：全文用**弯引号** `“ ”`（U+201C / U+201D），不用直角引号 `「 」`；图内文字同样适用。

**篇幅与密度**：散文承担因果、过渡、判断；条目承担并列信息。数据密度不超过一段的 40%。连续三段都以“第一/第二”或“路径 X”开头，就要打散重组。

---

## 3. 语气分层（重要）

技术深度文章面向工程师时，**允许并在意语气分层**：

- **条目列表内**：用书面语。落点词用“启示 / 前提 / 风险 / 上限”，避免“根本立不起来”“图一个”这类口语
- **章节导语与过渡**：可用口语，承担亲切感
- **收口句**：介于两者之间，允许带个人判断（“可这只是我的推断”）

判断方法：列表一旦采用“上述分析对工程实践有三点启示”这样的学术句式，列表内的条目也必须同步书面化，否则同一条目里会出现“书面标题 + 大白话解释”的割裂。

## 4. 自查清单

- [ ] 每个大标题都是直白句子，无设问、无比喻、无悬念
- [ ] 有先后关系的内容用了编号，并列内容用了条目，没有混用
- [ ] 每个条目都符合“**名词（英文）**：一句话机制（括号补注）”格式
- [ ] 没有单条超过 150 字的条目
- [ ] 每条最多一个数字，且数字都能在表或正文里找到出处
- [ ] 每节末尾都有且只有一句“关键在于/也就是说”收口句
- [ ] 全文无感叹号、无直角引号、无“首先/其次/综上所述”类套话
- [ ] 没有“本文将从…”“接下来我们看…”这类旁白
- [ ] 列表内外语气一致（列表内书面、列表外可口语，但不能同一条目内混用）

## 5. 怎么给 AI Agent 下指令

**最短指令**（本文件已在上下文时）

> 按“要点式技术拆解”写作规范，写一篇关于 XXX 的文章。

**完整指令**（对方没有本文件时）

> 按“要点式技术拆解”写，规则如下：
> 1. 大标题用一句直白的话说清这节讲什么，不要设问句、不要比喻句；
> 2. 有先后关系的流程用 `1.` `2.` 编号，每步一句话；
> 3. 并列的技术或方法用项目符号，每条写成“**加粗名词（英文名）**：一句话讲机制（括号里补一句解释）”，不要展开成段，每条不超过 150 字；
> 4. 每一节末尾补一句以“关键在于，”或“也就是说，”开头的收口句；
> 5. 全文用弯引号 `“ ”`，不用直角引号；不要 emoji；不要“首先/其次/综上所述”这类套话。
> 照这个结构和句式写，不要改成散文段落。

**只报名字是不够的**。“要点式”“清单体”在不同 Agent 那里会被理解成“多加几个项目符号”，然后每条内容依旧是长句。必须同时给**名称 + 骨架描述 + 一个示例片段**，并明确补一句“不要改成散文段落”。示例的作用最大。

## 6. 可配置项

| 配置 | 默认 | 可选 | 说明 |
|---|---|---|---|
| emoji 章节标记 | 关闭 | 开启 | 开启后用 `💡` `🔬` 等代替“一、二、三”做分节标记 |
| 引号风格 | 弯引号 `“ ”` | 直角引号 `「 」` | 全文与图内文字保持统一 |
| 大标题句式 | 直白陈述 | 短标题 + 冒号 | 开启 emoji 时通常配套使用 |
| 条目末尾数字 | 最多一个 | 不要数字 | 面向非技术读者时可全部去掉 |

## 7. 这个写法解决什么问题

技术文最常见的两种失败：一是把并列信息写成连贯长句，读者找不到第二条在哪里；二是把有顺序的流程写成一段话，读者读三遍才理清先后。四层骨架分别管住这两件事——条目管住并列，编号管住顺序，直白标题管住导航，收口句管住“读完这一节我该记住什么”。

一句话概括：**让每一层只干一件事，让读者扫一眼就知道信息的形状。**
